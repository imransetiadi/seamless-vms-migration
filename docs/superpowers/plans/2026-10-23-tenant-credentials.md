# Per-tenant credentials — implementation plan (2026-10-23)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task.

**Goal.** The release is 0.5.0 (owner decision 1). The plan answers PRD §9's 0.2.0 item
"per-tenant credentials" and PRD §10's "Tenant credentials (or admin with role assignment) on both clouds", which no
FR, design or code covered:
- An OpenStack or RHOSO provider holds, beside its own credential, an application credential per Keystone project,
  written by an admin, write-only, stored as `provider-{id}.project-<16 hex>`.
- A plan names its source project and its destination project (`source_project`, `destination_project`); null keeps
  0.4.0's rule, the provider's own credential, so a 0.4.0 plan runs unchanged.
- Each step acts with the credential SDD §27.5 names: the work inside a project with the plan's project credentials,
  `member` in most cases; the check, the storage pools, Placement, the flavor import, the handover's source half and a
  `member` project's floating IP reservation with the provider's own. A project credential that is missing, fails or
  expired is never replaced by the provider's.
- The provider check checks each project credential; four findings and a cutover gate rule guard roles, keypairs and
  expiry.
- VMware plans are unchanged. Per-tenant credentials are a Technology Preview until LAB-TC01–LAB-TC06 pass.

**Spec:** SDD §27 and D20. Each item becomes binding when its task moves it into the section §27.12 names. The PRD changes with TC1.

**Decisions:** the owner took the ten defaults of SDD §27.11 as written on 2026-10-23 (D20).
The research behind the design was done on 2026-10-23: Keystone's application credential guide and its identity API
reference (application credentials, OS-TRUST), Nova's, Neutron's, Placement's and Octavia's policy references, Cinder's
manage-existing flow and its volume transfer guide, os-migrate's design notes, CVE-2022-2447. The pull request that
proposes this plan lists the sources.

## Rules for every task

- **The SDD comes first.** The amendment that makes a task's item binding is its own commit, by the controller
  (CLAUDE.md §1, §3), and it moves the item from §27 into the section §27.12 names. The SDD-reading tests stay green:
  - a route enters §12's table with its task and `test_role_matrix`'s `ROUTES` in the same pull request, since
    `test_every_route_is_documented_in_sdd_12` and `test_the_role_matrix_covers_every_route_sdd_12_lists` read both;
  - a finding enters §9.3 with `planning/preflight.CATALOG`, the shared fixtures (`eligibility_cases.json` and
    `finding_catalog.json`, rewritten in their exact formats), the dashboard's `findingCatalog.ts` and mock, and
    QASuite FR-04's counts (`test_the_qasuite_counts_the_mocks_codes_and_the_shared_finding_cases`); its tests are
    named `test_finding_<code>` (`test_each_finding_code_has_a_test_named_for_it`);
  - no event kind is added: `provider.credentials_updated` gains data keys only; no variable is added to §15.1 and no
    metric to §18.
- **TDD.** The named tests fail first, for the stated reason, then pass. Mutants of the new logic are killed. A test
  named here keeps its name.
- **Tracks.** Track ownership is as in CLAUDE.md §3; no collection change is planned (track A). Where a contract binds
  two tracks (the provider's fields, the findings), the task's pull request carries one commit per track.
- **QASuite.** Each task's pull request adds its QASuite rows (track D), naming the tests it landed.
- **One selection rule.** Every step takes its credential from one function of the control plane, which reads the
  plan's `source_project` and `destination_project` and §27.5's table; no executor, helper or route picks a
  credential on its own. The fakes record which credential each call came with, and a test fails a step that used the
  provider's credential where §27.5 names the plan's, or the reverse.
- **Never a fallback.** A test that expects a missing, failing or expired project credential to be replaced by the
  provider's means the design is wrong.
- **Synthetic fixtures:** project ids of 32 hex digits made up in the test, project names `tenant-a` and `tenant-b`,
  application credential ids and secrets generated in the test; no real cloud. A secret never reaches a log line, an
  event, an error, a check report or a test's failure message.
