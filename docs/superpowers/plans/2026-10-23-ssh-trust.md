# SSH trust on the data path — implementation plan (2026-10-23)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task.

**Goal.** The release is 0.5.0 (owner decision 1). The plan answers D8 and Security.md's SEC-02
(host keys not verified) and SEC-06 (an unrestricted link key), threats C3-01 and C3-06, which Security.md and D8
planned for 0.2.0 and no release closed:
- Every conversion host's key is known before Seamless first connects to it: injected when Seamless creates the
  host, read from its console otherwise, or declared by the operator. No key is ever learned from a connection.
- Every hop of the data path checks it with `StrictHostKeyChecking=yes`: the modules' ssh and scp, Ansible, the
  destination host's link to the source host, and a VMware destination's conversion host.
- A refused key fails at once and for good, and a cutover checks its hosts and its link before the source stops.
- The link key is made per run on the destination host and held on the source host to a forced command that admits
  only the run's own transfer. It goes when the run ends.
- `SEAMLESS_ANSIBLE_HOST_KEY_CHECKING` stays, `true` by default once every hop is pinned, and governs every hop.

**Spec:** SDD §26 and D8. Each item becomes binding when its task moves it into the section §26.11 names. The PRD's NFR-06 and §9 change with ST1.

**Decisions:** the owner took the ten defaults of SDD §26.10 as written on 2026-10-23 (D8).
The research behind the design was done on 2026-10-23: OpenSSH's manual pages, source and release notes,
cloud-init's documentation and source, Nova's API and policy references, Ansible's ssh connection plugin, the VMware
kit 2.2.7's playbooks and Repology's package table. The pull request that proposes this plan lists the sources.

## Rules for every task

- **The SDD comes first.** The amendment that makes a task's item binding is its own commit, by the controller
  (CLAUDE.md §1, §3), and it moves the item from §26 into the section §26.11 names. The SDD-reading tests stay green:
  - an event kind enters §4.3, `events.py` and the dashboard's `PERSISTED_EVENT_KINDS` in one task, since
    `test_event_kinds_match_sdd_4_3_and_the_dashboard` reads all three;
  - a finding code enters §9.3 with the catalog, its shared fixtures in their exact formats and its
    `test_finding_<code>` tests, since `test_catalog_matches_sdd_9_3` and
    `test_each_finding_code_has_a_test_named_for_it` read them;
  - the setting's new default enters §15.1 with `Settings`;
  - SSH trust adds no route. The provider's new fields enter §4.2 and §12's provider rows with ST2.
- **TDD.** The named tests fail first, for the stated reason, then pass. Mutants of the new logic are killed. A test
  named here keeps its name.
- **Tracks.** Track ownership is as in CLAUDE.md §3. Where a shared contract binds two tracks (an event kind, the
  provider's fields), the task's pull request carries one commit per track.
- **QASuite.** Each task's pull request adds its QASuite rows (track D), naming the tests it landed.
- **Real ssh, no network.** A test that claims a key is accepted or refused runs a real `sshd` on 127.0.0.1, as the
  test's own user, with host keys, client keys and an `authorized_keys` the test made with `ssh-keygen` in a
  temporary directory, and a real `ssh` client. It is skipped where no `sshd` binary is installed. A mock alone never
  proves a refusal.
- **No secret in a test or a log.** Every key is made in the test. Console texts are synthetic, with addresses in
  192.0.2.0/24 and 198.51.100.0/24 (RFC 5737). A private key never reaches a log line, an event, a failure message or
  a test's failure output.
- **Upstream stays upstream.** The collection without the new variables behaves as today's upstream, and a test says
  so.
