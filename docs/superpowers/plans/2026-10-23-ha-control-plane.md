# HA control plane — implementation plan (2026-10-23)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task.

**Goal.** The release is 0.5.0 (owner decision 1). The plan answers FR-27 ("HA control plane
(leader election)"), PRD §9's 0.2.0 item "HA (PostgreSQL leader election)" and D2:
- On OpenShift and Kubernetes two replicas of the control plane run on two nodes. A lease in PostgreSQL makes one of
  them the leader, and only the leader runs the orchestrator.
- A deposed leader writes nothing, because the store checks the lease's epoch in every write. It starts nothing on a
  cloud, and it kills its playbooks before another replica may take over.
- The new leader resumes the migrations from their checkpoints, as a restart does, about 35 s after the old one was
  lost (about 12 minutes on a lost node today).
- A follower relays the API and the event stream to the leader, so both replicas serve and both are ready.
- Compose, Podman and SQLite stay single-replica. On PostgreSQL the lease still keeps a second server from running a
  second orchestrator.
- HA is a Technology Preview until the lab's failover cases pass (SDD §25.10).

**Spec:** SDD §25 and D2. Each item becomes binding when its task moves it into the section §25.12 names. The PRD's FR-27 and §9 change with HA1.

**Decisions:** the owner took the ten defaults of SDD §25.11 as written on 2026-10-23 (D2).
The research behind the design was done on 2026-10-23: PostgreSQL's and Kubernetes' documentation, client-go's
leader election package, PgBouncer's feature table and Martin Kleppmann's article on fencing tokens. The pull request
that proposes this plan lists the sources.

## Rules for every task

- **The SDD comes first.** The amendment that makes a task's item binding is its own commit, by the controller
  (CLAUDE.md §1, §3), and it moves the item from §25 into the section §25.12 names. The SDD-reading tests stay green:
  - an event kind enters §4.3, `events.py` and the dashboard's `PERSISTED_EVENT_KINDS` in one task, since
    `test_event_kinds_match_sdd_4_3_and_the_dashboard` reads all three;
  - a variable enters §15.1 with `Settings`;
  - a metric enters §18 with `/metrics`;
  - HA adds no route. A field of `/health`'s body enters §12's row of `/health` with its task.
- **TDD.** The named tests fail first, for the stated reason, then pass. Mutants of the new logic are killed. A test
  named here keeps its name.
- **Tracks.** Track ownership is as in CLAUDE.md §3. Where a shared contract binds two tracks (the event kinds, the
  health body), the task's pull request carries one commit per track.
- **QASuite.** Each task's pull request adds its QASuite rows (track D), naming the tests it landed.
- **Two replicas in one test process.** The tests drive two electors and two orchestrators on one SQLite file, and on
  PostgreSQL when `SEAMLESS_TEST_PG_URL` is set. A test that needs PostgreSQL's row locks is skipped without it, as
  the store's PostgreSQL tests are. No test talks to a cluster: the manifests are read as YAML, CI's kustomize job
  renders them, and `seamless-ctl.sh` runs against the fake cluster (`tests/fake_kube.py`).
- **Short leases, real processes.** Tests hand the elector leases of a second or two, never wait out the 30 s
  default, and never fake the database's clock: the lease's SQL reads it. The kill is tested on real process groups,
  a `sleep` started in a session of its own, never on a mock alone.
- **One resume path.** A new leader goes through `Orchestrator.start()`. A test that needs another resume path means
  the design is wrong.
- **Synthetic fixtures:** replica host names such as `seamless-a` and `seamless-b`, addresses in 192.0.2.0/24
  (RFC 5737), tokens generated in the test; no customer host, no real cluster. A token never reaches a log line, a
  relayed error or a test's failure message.
