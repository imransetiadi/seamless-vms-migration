# GPU workloads — implementation plan (2026-10-20)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task by task.

**Goal (release 0.3.0, Technology Preview; PRD goal G8 and FR-35–FR-41 as G14 proposes them):** VMs with an NVIDIA
vGPU, MIG-backed vGPU profiles included, or with a GPU passed through to the guest migrate from VMware vSphere, RHOSP
17.1 and community OpenStack to RHOSO 18.0 or a community destination (SDD §21) instead of being blocked. A plan maps
each source GPU explicitly to a destination GPU flavor, the pre-flight checks the destination's free GPU capacity in
Placement, the cutover gate reads it again before the source stops, and the verification confirms the server holds its
GPU. Validated in simulation only until the lab tasks run on GPU hosts (SDD §22.14).

**Spec:** SDD §22 (binding once each task moves its item into the section §22.13 names), D16, D17, §1, the note under
§9.3's table; PRD G8 and FR-35–FR-41 (G14); QASuite (G13); Security.md (G13).

**Decisions taken:**

- The owner, 2026-10-20 (SDD D16): GPU VMs get no wave tier of their own and never go into the pilot wave; one GPU
  flavor per GPU key in a plan, a smaller flavor being a warning and other sizes going into another plan (a per-VM GPU
  flavor is D17, after the Technology Preview); the plan's GPU mapping is the opt-in, with no switch; the network
  cut-over hooks and the Octavia/Heat helpers move from 0.3.0 to 0.4.0.
- The controller, without Jev: the `jev` MCP server was connected but this session had no provider key (CLAUDE.md §4:
  continue without it). Each choice and its reason, for `jev_decide` to re-check once a key is set:
  - **Mapping shape.** `Mappings.gpus` maps a VMware GPU key (the vGPU profile, or `vendor:device` for a passthrough
    device) to one destination flavor; an OpenStack GPU VM keeps its flavor mapping, since its GPU is part of its
    flavor and the VMs of one flavor have one size. This is the owner's shape (profile to flavor). It needs no second
    mapping for OpenStack and keeps every `Mappings` value a plain string.
  - **Pools.** A pool is a resource class with its required and forbidden traits, read from Placement's allocation
    candidates (one request per pool at microversion 1.29), and checked per pool and per resource class. This is
    exact in the usual case of one vGPU per request group and needs no host names. Nova's full request translation
    (CPU pinning, image traits, aggregates) was rejected as too easy to get wrong.
  - **Unknown never holds the gate; a failed read does.** A 403 or a missing Placement endpoint makes capacity
    `unknown`, which the pre-flight warns of and the gate cannot improve on. A timeout or a 5xx answer may hide a full
    pool, so the source must not stop on it.
  - **Declared profiles** (`Provider.gpu_profiles`) per flavor: no OpenStack API names a flavor's vGPU framebuffer,
    so `MAP_GPU_DOWNSIZED` compares only what an operator declared, never a guess.
  - **`GUEST_GPU_DRIVER` for every strategy** (the owner's sketch named the VMware strategies): the guest driver must
    suit the destination host's vGPU manager whatever the source. For VMware the message adds that virt-v2v leaves the
    driver as it is.
  - **VMware passthrough eligibility**, a fact found while designing: vSphere supports no snapshot of a VM with a
    DirectPath I/O device (vSphere 8 Snapshot Limitations), and the kit reads every copy from its `osm-snap` snapshot.
    So `vmware_warm` is ineligible for such a VM, and `vmware_cold` is eligible only while the VM is powered off.

## Rules for every task

- The SDD amendment that makes the task's item binding comes first, in its own commit, by the controller (CLAUDE.md
  §1, §3): it moves the item from §22 into the section §22.13 names (G4 also replaces the note under §9.3's table). The
  SDD-reading tests stay green: a finding code enters §9.3 with its catalog entry (G4), the event kind enters §4.3 with
  `events.py` and `types.ts` (G6), and the gauge enters §18 with `/metrics` (G6).
- TDD: the named tests fail first for the stated reason, then pass; mutants of the new logic are killed. A test named
  here keeps its name.
- Track ownership as CLAUDE.md §3. Where a shared fixture holds two tracks to one contract, the task's pull request
  carries one commit per track, so that neither suite goes red in between: G2 (the VMware provider stops writing GPU
  extra specs, and `lib/readiness.ts` reads `vm.gpus`), G3 (`check_report_keys.json` and the mock's check), G4
  (`finding_catalog.json`, `findingCatalog.ts` and QASuite FR-04's code count), G5 (`eligibility_cases.json`,
  `probe_suggestion_cases.json` and the mock), G6 (the event kind and `types.ts`).
- Each task's pull request adds its QASuite rows (track D) naming the tests it landed:
  `test_every_test_qasuite_names_exists` refuses a row that names a test that does not exist yet.
- Fixtures are synthetic: Placement answers are recorded by hand, with made-up host names such as `gpu-host-a` that
  the security test (G3) looks for; no customer host, no real hostname.
- Technology Preview: no text, test name, doc or commit claims that GPU migration was validated on hardware until G15's
  cases pass (SDD §22.14).

## Review focus

1. The source never stops without a fresh read that found room. G6's first test empties the pool after validation and
   checks that the source's power and the downtime clock never move.
2. Nothing is guessed: a 403 or a missing endpoint reads `unknown` and warns; a failed read holds the gate (G3, G6).
3. A GPU VM is never matched by size or by name and never pre-staged. A mapping to a flavor without a GPU keeps it
   blocked (G4).
4. No Placement provider name or uuid leaves the read, in any field, event, log line or check detail (G3, G8).
5. VMware passthrough: `vmware_warm` ineligible, `vmware_cold` only powered off (G5). The kit gets `flavor_uuid`, and
   `gpu_flavor` catches a server created without the GPU (G7, G8).
6. Every GPU surface says Technology Preview, and nothing claims hardware validation (G10–G13).
